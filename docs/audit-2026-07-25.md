## 1. Critiques

### C1. La clé API Google fuite vers le client via l'erreur `SCAN_FAILED`

**Réf.** : [server/domain/scan/index.ts:101](server/domain/scan/index.ts:101) et [:288](server/domain/scan/index.ts:288), [server/domain/scan/infrastructure/graphql/mutations.ts:55](server/domain/scan/infrastructure/graphql/mutations.ts:55)

Les deux appels Gemini passent la clé en query string :

```ts
}>(`${GEMINI_API_URL}?key=${googleApiKey}`, {
```

Quand Gemini répond en erreur HTTP (429 de quota, 400, 5xx, des cas courants), `ofetch` lève une `FetchError` dont le message contient l'URL complète. Le resolver relaie ce message tel quel :

```ts
} catch (error) {
  const message = error instanceof Error ? error.message : 'Scan failed'
  return domainError('SCAN_FAILED', message)
}
```

N'importe quel utilisateur authentifié qui déclenche un scan pendant un incident Gemini reçoit donc l'URL complète, clé comprise, dans `errors[0].message`. La clé part aussi dans Sentry et dans les logs.

**Refactor** :

1. Passer la clé en en-tête, jamais en URL : `headers: { 'x-goog-api-key': googleApiKey }` (supporté par l'API Gemini).
2. Ne jamais relayer `error.message` brut au client :

```ts
} catch (error) {
  logger.error('scan failed', error)
  return domainError('SCAN_FAILED', 'The scan could not be completed')
}
```

3. Faire tourner `NITRO_GOOGLE_API_KEY` après correction, la clé ayant pu être exposée.

### C2. `importData` corrompt toutes les dates : le round-trip export puis import casse le compte

**Réf.** : [server/domain/portability/use-case.ts:74-95](server/domain/portability/use-case.ts:74) et [:106-123](server/domain/portability/use-case.ts:106)

`exportData` sérialise avec `JSON.stringify`, donc les `Date` deviennent des chaînes ISO. `importAll` fait `JSON.parse` puis valide avec `looseRecord = z.looseObject({ userId: z.string() })` : seul `exportedAt` passe par `dateSchema` (ligne 116). Les dates internes (`createdAt`, `updatedAt`, `purchase.date`, `date` du journal, `consumedDate`, `expiresAt`) restent des **chaînes** et sont écrites telles quelles dans Firestore via `bulkSave`.

Conséquences après un import :

- `genericDataConverter` ne reconvertit que les `Timestamp`, donc les relectures renvoient des `string` là où le domaine attend `Date`.
- `BeverageQuery.paginateInMemory` ([server/domain/beverage/query.ts:139](server/domain/beverage/query.ts:139)) appelle `beverage.updatedAt.getTime()`, ce qui lève un `TypeError` et produit un 500 sur la liste. Même chose pour `JournalQuery.historyOf` et le tri du dashboard.
- Les `orderBy('createdAt')` mélangent deux types Firestore : les documents importés sortent regroupés à part ou disparaissent des curseurs.

Aucun test ne couvre la portabilité, ce qui explique que le bug soit passé.

**Refactor** : réhydrater les dates à l'import via de vrais schémas Zod par domaine (voir M1), ou a minima :

```ts
const isoDate = z.iso.datetime().transform((value) => new Date(value))
const beverageRecord = z.looseObject({
  userId: z.string(),
  createdAt: isoDate,
  updatedAt: isoDate,
  purchase: z.looseObject({ date: isoDate.optional() }).optional(),
})
```

Et ajouter un test d'intégration `exportAll → JSON.stringify → importAll → BeverageQuery.list` qui échoue avant la correction.

## 2. Majeurs

### Backend

#### M1. `importData` : validation quasi inexistante, cast `as`, champs arbitraires, non-atomicité

**Réf.** : [server/domain/portability/use-case.ts:77-95](server/domain/portability/use-case.ts:77), [:110](server/domain/portability/use-case.ts:110)

Trois problèmes au même endroit, sur la frontière la plus exposée du système (du JSON fourni par le client) :

1. **Cast au lieu de validation** : `stamp(envelope.wines) as Beverage[]`. `docs/domain-guide.md` et `docs/code-style.md` interdisent explicitement `as MyType` à une frontière. Aucune primitive n'est appliquée : un `rating: 999`, un `row: -5`, une `color: "bleu"` entrent en base sans contrôle.
2. **`z.looseObject` laisse passer tous les champs inconnus** : un payload peut injecter des clés arbitraires, gonfler les documents Firestore à volonté et polluer les exports suivants.
3. **Non-atomicité** : les six `replaceAllForUser` tournent en parallèle et chacun fait wipe puis restore. Un échec au milieu laisse un compte à moitié vidé, sans erreur typée côté domaine.

**Refactor** : un schéma Zod strict par collection réutilisant les primitives de chaque domaine, `z.strictObject` (ou au minimum un `pick` des champs connus), et validation complète **avant** le premier wipe.

#### M2. `placeBottle`/`moveBottle` : entiers non validés (500) et aucune borne contre la grille

**Réf.** : [server/domain/cellar/infrastructure/graphql/mutations.ts:35-36](server/domain/cellar/infrastructure/graphql/mutations.ts:35) et [:62-63](server/domain/cellar/infrastructure/graphql/mutations.ts:62), [server/domain/cellar/primitives.ts:34-52](server/domain/cellar/primitives.ts:34), [server/domain/cellar/command.ts:64-98](server/domain/cellar/command.ts:64)

Deux défauts distincts :

- Les resolvers appellent `CellarRow(row)` / `CellarCol(col)` directement. Sur `row: -1`, le `ZodError` n'est pas rattrapé, ce qui donne un `INTERNAL_SERVER_ERROR` 500 et du bruit Sentry au lieu d'un `BAD_USER_INPUT`. C'est l'inverse du pattern appliqué trois lignes plus haut dans le même fichier (`parseDimensions` catch puis `badUserInput`), et une violation de la règle « resolvers receive pre-validated branded args » de `docs/api-patterns.md`.
- `CellarRow`/`CellarCol` n'ont pas de borne haute, et ni `placeBeverage` ni `moveBottle` ne confrontent la position à `CellarQuery.config`. L'API accepte donc de placer une bouteille en `row: 9999` sur une grille 10x10. La bouteille compte dans `placedCount`, reste invisible dans la grille, et `reconfigure` refuse ensuite tout redimensionnement (`outOfBounds > 0`) sans explication compréhensible.

**Refactor** : des scalars GraphQL `CellarRow`/`CellarCol` (cohérent avec le reste du schéma) ou un try/catch vers `badUserInput`, plus un garde métier dans la commande :

```ts
const { rows, cols } = await CellarQuery.config(userId)
if (row >= rows || col >= cols) return 'position-out-of-grid' as const
```

#### M3. Paires d'écritures cellar/journal non atomiques

**Réf.** : [server/domain/cellar/command.ts:82-97](server/domain/cellar/command.ts:82) (place) et [:103-116](server/domain/cellar/command.ts:103) (remove)

`moveBottle` (lignes 143-193) enveloppe ses écritures dans `atomically` avec un commentaire qui explique pourquoi. Les deux autres commandes du même fichier ne le font pas :

- `placeBeverage` fait `repository.save(...)` puis `JournalCommand.bottleIn(...)`. Si le journal échoue, la bouteille est placée sans événement d'entrée.
- `removeBeverage` fait `JournalCommand.bottleOut(...)` puis `repository.remove(...)`. Si le remove échoue, le journal affirme une sortie alors que la bouteille est toujours en cave. L'ordre aggrave le cas : l'écriture la plus importante vient en dernier.

Le journal alimente le dashboard et l'historique par vin, donc l'incohérence est directement visible.

**Refactor** : passer les deux commandes en `atomically(batch => …)`. `repository.save` et `JournalCommand.bottleIn/Out` acceptent déjà un `batch`, le changement est mécanique.

#### M4. Course check-then-write sur l'occupation d'un slot

**Réf.** : [server/domain/cellar/command.ts:78-79](server/domain/cellar/command.ts:78) et [:127-135](server/domain/cellar/command.ts:127)

`findByPositionForUsers` puis `save` sans verrou : deux membres d'un ménage qui placent ou déplacent une bouteille sur le même slot au même moment passent tous les deux le garde `position-occupied`, et le slot finit doublement occupé, état que l'UI de grille ne sait pas représenter. Le commentaire de `moveBottle` (lignes 140-142) reconnaît la limite. Le partage de cave par ménage rend le scénario plausible, et `transactionally` existe déjà dans [server/utils/firestore.ts:130](server/utils/firestore.ts:130).

**Refactor** : porter le couple lookup-position plus écriture dans `transactionally` (`tx.get(query)` est supporté par firebase-admin).

#### M5. Autorisation des invitations plus laxiste que le contrat affiché

**Réf.** : [server/domain/household/command.ts:144-154](server/domain/household/command.ts:144), à comparer avec la description de `revokeHouseholdInvitation` dans [server/domain/household/infrastructure/graphql/mutations.ts](server/domain/household/infrastructure/graphql/mutations.ts) et [server/domain/household/query.ts:22-23](server/domain/household/query.ts:22)

`revokeInvitation` vérifie seulement l'appartenance au ménage, jamais `actor.role === 'owner'`, contrairement à `removeMember`. La description GraphQL publiée (donc le contrat côté iOS) promet owner-only. En pratique, n'importe quel membre peut révoquer les codes, et aussi en créer (`createInvitation` ne vérifie pas non plus le rôle). Un membre fraîchement arrivé peut inviter des tiers dans la cave partagée ou saboter les invitations du propriétaire.

**Refactor** : trancher le modèle (owner-only ou tout-membre) puis aligner code **et** descriptions. Pour owner-only, l'outcome `'not-owner'` est déjà mappé dans `householdError` :

```ts
if (actor.role !== 'owner') return 'not-owner' as const
```

### iOS

#### M6. La date d'achat ne s'affiche jamais dans le formulaire d'édition

**Réf.** : [ios/Vinarium/Features/Wines/WineDetailView.swift:449-452](ios/Vinarium/Features/Wines/WineDetailView.swift:449)

```swift
if let dateString = detail.purchaseDate {
    parsedPurchaseDate = ISO8601DateFormatter().date(from: dateString)
}
```

Le serveur sérialise le scalaire `DateTime` avec `value.toISOString()` ([server/domain/shared/graphql/builder.ts:43](server/domain/shared/graphql/builder.ts:43)), qui produit toujours des fractions de seconde. Un `ISO8601DateFormatter()` nu échoue systématiquement sur ce format, ce pour quoi `GraphQLHelpers.parseISO8601` essaie les deux variantes. Résultat : le formulaire affiche toujours « Ajouter » à la place de la date d'achat existante ; l'utilisateur ne peut ni la voir ni la corriger, et s'il touche « Ajouter » il l'écrase par la date du jour sans le savoir.

**Refactor** (une ligne) :

```swift
parsedPurchaseDate = detail.purchaseDate.flatMap { GraphQLHelpers.parseISO8601($0) }
```

#### M7. Prix à virgule décimale silencieusement perdu

**Réf.** : [ios/Vinarium/Features/Wines/components/organisms/WineEditForm.swift:297](ios/Vinarium/Features/Wines/components/organisms/WineEditForm.swift:297) et [ios/Vinarium/Features/Scan/components/pages/ScanReviewPage.swift:488](ios/Vinarium/Features/Scan/components/pages/ScanReviewPage.swift:488)

Les deux champs prix utilisent `.keyboardType(.decimalPad)`, qui affiche une virgule sur un clavier français. `Double("12,50")` retourne `nil`, donc le prix tapé n'est jamais envoyé, sans message. L'incohérence est visible dans le même fichier : le degré d'alcool gère la virgule ([ScanReviewPage.swift:485](ios/Vinarium/Features/Scan/components/pages/ScanReviewPage.swift:485)).

**Refactor** : centraliser un parseur tolérant et l'utiliser pour les trois champs.

```swift
extension Double {
    init?(userInput: String) {
        self.init(userInput.replacingOccurrences(of: ",", with: "."))
    }
}
```

#### M8. Les échecs de rechargement sont invisibles dès qu'un contenu est affiché

**Réf.** : [DashboardView.swift:13-24](ios/Vinarium/Features/Dashboard/DashboardView.swift:13), [WineDetailView.swift:29-57](ios/Vinarium/Features/Wines/WineDetailView.swift:29) et [:374-387](ios/Vinarium/Features/Wines/WineDetailView.swift:374), [CellarView.swift:16-20](ios/Vinarium/Features/Cellar/CellarView.swift:16), [WineListContent.swift:19](ios/Vinarium/Features/Wines/components/organisms/WineListContent.swift:19)

Dans les quatre écrans, la branche d'erreur n'est atteinte que si le contenu est vide. Un refetch qui échoue (pull-to-refresh, retour d'onglet, post-mutation, notification `.vinariumDataDidReload`) pose `error` mais la vue continue d'afficher les données périmées sans aucun retour : l'utilisateur croit voir un état à jour. Les reloads déclenchés par `onChange(of: selectedTab)` ([DashboardView.swift:32-36](ios/Vinarium/Features/Dashboard/DashboardView.swift:32)) sont en plus sans loader, en tension avec la règle projet « tout appel réseau affiche un chargement » (le voile de `WineDetailView.swift:68-76` montre le bon pattern).

**Refactor** : présenter l'erreur de refresh indépendamment du contenu, en réutilisant `ErrorPresenter` et `.errorAlert(...)` dans ces coordinateurs.

#### M11. `parseISO8601` alloue deux `ISO8601DateFormatter` par appel, sur le chemin chaud

**Réf.** : [ios/Vinarium/Shared/GraphQLHelpers.swift:40-46](ios/Vinarium/Shared/GraphQLHelpers.swift:40), appelé 3 fois par vin dans [Wine+GraphQL.swift:39,45,46](ios/Vinarium/Features/Wines/Wine+GraphQL.swift:39) et dans `DashboardAPI`

`ISO8601DateFormatter` est coûteux à créer. Chaque page de 15 vins en instancie une centaine sur le main actor, le mapping se faisant dans des ViewModels `@MainActor`.

**Refactor** (le formatter est thread-safe, le `static let` est sûr) :

```swift
private static let isoWithFraction: ISO8601DateFormatter = {
    let f = ISO8601DateFormatter()
    f.formatOptions = [.withInternetDateTime, .withFractionalSeconds]
    return f
}()
private static let isoPlain = ISO8601DateFormatter()

static func parseISO8601(_ string: String) -> Date? {
    isoWithFraction.date(from: string) ?? isoPlain.date(from: string)
}
```

## 3. Mineurs

### Backend

- **m1. Course sur l'usage unique d'un code d'invitation.** [household/command.ts:70-99](server/domain/household/command.ts:70) : le statut `used` est lu hors transaction, donc deux utilisateurs qui consomment le même code simultanément rejoignent tous les deux le ménage (le second écrase `usedBy`). Impact borné, `transactionally` réglerait le cas.
- **m2. Orchestration métier du scan dans le resolver.** [scan/infrastructure/graphql/mutations.ts:37-54](server/domain/scan/infrastructure/graphql/mutations.ts:37) : gate de quota, métrage post-scan et télémétrie admin vivent dans le resolver, alors que `docs/domain-guide.md` réserve ce type d'orchestration multi-domaines à un `use-case.ts` (`ScanUseCase.scanAndMeter`). La règle « un scan raté ne coûte rien » n'est aujourd'hui testable qu'au niveau GraphQL.
- **m3. `completeOnboarding` écrase le profil, flag `admin` compris.** [user/command.ts:8-10](server/domain/user/command.ts:8), [user/infrastructure/repository.ts:26-35](server/domain/user/infrastructure/repository.ts:26) : `saveProfile` fait un `set` complet sans garde ni merge. Rejouer la mutation réinitialise `onboardingCompletedAt` et efface `admin: true`, posé à la main en base. Corriger avec `{ merge: true }` ou un refus si déjà onboardé.
- **m4. Enchaînements de use-cases non atomiques.** [beverage/use-case.ts:23-27](server/domain/beverage/use-case.ts:23), [cellar/use-case.ts:19-30](server/domain/cellar/use-case.ts:19) : un échec de la seconde écriture laisse un beverage sans provenance ou une bouteille sortie sans note. `removeCompletely` montre le bon pattern.
- **m5. Scalar `DateTime` non validé en entrée.** [shared/graphql/builder.ts:44](server/domain/shared/graphql/builder.ts:44) : `new Date(value as string)` produit une `Invalid Date` qui explose plus loin en 500 au lieu d'un `BAD_USER_INPUT` au parse. Aligner sur le `validatedParse` de `scalars.ts` avec `z.iso.datetime()`.
- **m6. `memoizedPerRequest` met en cache les promesses rejetées.** [system/request-cache.ts:11-20](server/system/request-cache.ts:11) : une erreur Firestore transitoire est rejouée par tous les appels suivants de la même requête. Ajouter `cache[key].catch(() => evict(key))`.
- **m7. Primitives nues et tableau optionnel dans le domaine tasting.** [tasting/types.ts:13-14](server/domain/tasting/types.ts:13) (`tastingNotes?: string`, `contacts?: string[]`) et [recommendation/types.ts:8](server/domain/recommendation/types.ts:8) : pas de brand, tableau optionnel interdit par `docs/code-style.md`, et `t.string()`/`t.stringList()` côté GraphQL alors que `PersonName` existe.
- **m8. Code mort : branches de tri inatteignables et `config().apiToken` inutilisé.** [beverage/infrastructure/repository.ts:12-19](server/domain/beverage/infrastructure/repository.ts:12) mappe `price`/`vintage`/`color`, mais `BeverageQuery.list` ne route vers `findPage` que pour `createdAt`/`updatedAt` (`CURSOR_SAFE_SORTS`). Ces branches sont mortes et dangereuses : aucun index composite correspondant n'existe, donc un futur appel donnerait un `FAILED_PRECONDITION` en prod. `config().apiToken` ([system/config/index.ts:19](server/system/config/index.ts:19)) est un vestige du client REST.
- **m9. Arguments `limit`/`offset` ni bornés ni validés.** [journal/…/queries.ts:9-11](server/domain/journal/infrastructure/graphql/queries.ts:9), [beverage/…/queries.ts:49](server/domain/beverage/infrastructure/graphql/queries.ts:49), [cellar/…/queries.ts:17-18](server/domain/cellar/infrastructure/graphql/queries.ts:17) : `journalEvents(limit: 500000)` lit tout le journal, `limit: -3` fait lever Firestore en 500. Un clamp suffit.
- **m10. Pagination offset du journal : coût de lecture croissant.** [journal/infrastructure/repository.ts:65-80](server/domain/journal/infrastructure/repository.ts:65) : Firestore facture les documents sautés, donc la page 20 coûte 300 lectures et plus. Un `startAfter` par doc-snapshot coûterait le même effort de code.
- **m11. `CellarRow.toLabel` produit des caractères invalides au-delà de la ligne 26.** [cellar/primitives.ts:42](server/domain/cellar/primitives.ts:42) : `String.fromCharCode(65 + row)` étiquette la ligne 27 `[` et la ligne 99 `¤`, alors que `CellarRows` autorise 100 lignes. Passer à un étiquetage type tableur (AA, AB) ou plafonner à 26.
- **m12. `scan-cache` sans TTL ni purge.** [scan/infrastructure/repository.ts](server/domain/scan/infrastructure/repository.ts) : une entrée par couple image/langue, jamais relue après un changement de format, jamais supprimée. ## 4. Points vérifiés et conformes

Utile pour le contexte, ces axes ont été contrôlés et ne présentent pas d'écart :

- **Règle N+1 respectée.** Les cinq satellites de `Beverage` (`cellar`, `consumption`, `gift`, `recommendation`, `history`) passent tous par les loaders de `server/domain/shared/graphql/loaders.ts`. `ownerName` s'appuie sur le `cellarScope` memoizé, à zéro lecture marginale. Les budgets de lecture sont assertés dans les tests.
- **Index Firestore conformes.** Croisement de chaque requête composite avec `firestore.indexes.json` : beverages (userId, createdAt DESC) et (userId, updatedAt DESC), cellar (userId, createdAt DESC) et (userId, row, col), journal (userId, date DESC) et (userId, type, date DESC), tasting (userId, favorite). Toutes couvertes. Aucun index déclaré n'est orphelin. Seule réserve : les branches mortes de `sortField` (m8) n'ont pas d'index, les supprimer clôt le sujet.
- **Aucune fuite de repository inter-domaines**, vérifiée par grep et par le test d'architecture `server/architecture.unit.test.ts` qui l'impose.
- Zéro `console.*`. Le quota est incrémenté en transaction avec éviction du cache memoizé. La vérification Apple ne fait confiance qu'à la signature. `firestore.rules` verrouille tout accès direct.
